How other harnesses stream

Four other agent harnesses solve the same problem the streaming path solves: provider SSE in, a normalized event stream out, tool calls dispatched, next turn. Their source was read directly (not docs). They agree on more than they disagree — and where they agree lines up almost exactly with the two spots our own path flagged as over-complex.

The four at a glance

Project Stack SSE Tool-call args Normalized event model
opencode TS / Bun / Effect both: AI SDK (default) + hand-rolled native raw string, parsed once at block-stop LLMEvent union
codex-rs Rust / tokio hand-rolled (eventsource-stream) server reassembles — no accumulation ResponseEvent enum
deepseek-harness TS / cordis DI hand-rolled (eventsource-parser) raw string, parsed once at execution StreamChunk + assembler
pi TS monorepo mixed: SDK (OpenAI) + hand-rolled (Anthropic) partial JSON re-parsed every delta Block / Message

Where all four agree

One normalized event union is the seam

Every project converges the providers onto a single internal event type with explicit start/delta/end framing — LLMEvent, ResponseEvent, StreamChunk, Block. Nothing downstream ever sees a provider's wire shape. We already have this: Stream_Event.

Tool args stay a raw string until finalize

Three of four accumulate argument fragments as a plain string and parse it exactly once — at block-stop (opencode) or at execution (deepseek); codex doesn't accumulate at all. Empty string becomes {}. No streaming JSON parser in the hot path.

A stream that ends early is an error

deepseek throws STREAM_CLOSED without [DONE]; codex emits "stream closed before response.completed". Truncation is a hard failure, not a soft flush — the same stance our decoder_finish already takes for Anthropic.

Malformed events degrade, never crash

codex skips an unparseable data: line with a trace! and continues; opencode marks spec-required fields optional so proxy quirks don't fail the decode. Matches our "never assert on peer input, return a validation error" rule.

Where they diverge

Two real forks in the road, both decisions we have to make in the rework.

SDK vs hand-rolled SSE

pi is pragmatic — it uses the OpenAI SDK's stream where it's clean and drops to raw ReadableStream parsing for Anthropic where the SDK is in the way. opencode is mid-migration from AI-SDK to its own native parsers and pays for maintaining both. codex and deepseek hand-roll over a small framing crate. For an Odin daemon there is no SDK to lean on — hand-rolled is the only option, which makes opencode's native design the closest reference.

When do tool-call args get parsed?

codex targets the Responses API and lets the server reassemble arguments — the finished FunctionCall arrives whole in output_item.done, so it deletes delta-stitching entirely. pi does the opposite: it re-parses partial JSON on every delta so a TUI can render half-typed arguments live. deepseek/opencode sit in the middle: accumulate raw, parse once. The live-render tax is only worth paying if a client actually shows streaming args.

What this says for our rework

Read against the two complexity call-outs on the streaming and json codecs pages, the external designs point at four concrete moves.

  1. Keep Stream_Event as the seam — it's the thing everyone else built.
    The one design decision all four validate. The rework is about the machinery around it, not the model itself.
  2. Collapse the three tool-arg sources to one.
    codex confirms the suspicion in the "three arg sources" call-out: for the Responses API the .done item carries full arguments, so openai_responses_finalize_tool's delta-accumulation path is likely dead. Prefer the done-item args; keep a raw-string accumulator only for Chat Completions, which genuinely fragments them.
  3. Separate the pump from the decode.
    Both codex (a spawned task feeding an mpsc ResponseStream) and opencode (framing → protocol.step → executor) split transport from a pure (state, event) → [state, events] decoder. That is exactly what the Completing/deferred-dispatch handshake in turn.odin is straining to do by hand — a cleaner split would make it a pure function plus a delivery queue.
  4. Shallow-envelope decode instead of parser rewind.
    codex decodes a flat header, switches on type, then strictly decodes the specific payload — unknown event names fall through, strict typing stays where it matters. That is a direct answer to the dec_find_tag "snapshot-and-rewind the whole parser to find the discriminator" complexity in the wire codec.

Per project — the one idea to steal

opencode

anomalyco/opencode · packages/llm/

The Framing / Protocol / Route three-layer split, and one generic tool-stream util keyed by number | string that handles all four provider grammars. Ignore the Effect ceremony and the transitional dual-runtime.

codex-rs

openai/codex · codex-api/src/sse/

String-dispatch envelope over a giant tagged enum, plus "history is the only accumulator — the next request is a pure projection of it," so tool outputs are never hand-threaded into the next call.

deepseek-harness

deepseek-ai/deepseek-harness

A named seam at every boundary: adapter → translate → BlockAssembler → loop. The assembler is straggler-tolerant — first close wins, deltas after a block-end are ignored — a good defensive invariant.

pi

earendil-works/pi · packages/ai/

The pragmatic SDK-where-clean, raw-where-not split — and a tolerant parseStreamingJson that always returns a valid object mid-token. Only worth it if a client renders streaming tool args.
