The provider rework, end to end

One page to understand the whole provider surface before we change it: how a streamed answer decodes (SSE), exactly who owns which bytes and for how long (the two-arena lifetime), why the request builders are the real weight, and what other harnesses — opencode, crush, pi — do at the same seams. The diagrams are live: step them, feed them bytes, toggle the markers.

The map — two halves, one seam

Everything in src/provider is a translation between one neutral shape and three provider dialects. The request half maps our wire.Message transcript out to a provider's JSON body; the response half maps a provider's streamed events in to a neutral Stream_Event. The seam in the middle is the whole point: nothing downstream of the decoder ever sees a provider's wire shape, and nothing upstream of the builder speaks a dialect.

response side · today

Settled. A generic framer + a per-provider decoder onto Stream_Event. Raw tool-args, deferred parse, graceful degradation — already matches the field.

request side · the weight

1,766 LOC across three forward-only builders that each re-walk the transcript. This is where the rework earns its lines — and what unblocks tail-caching.

the seam · keep it

Stream_Event is the one design every reference harness independently arrived at. The rework is the machinery around the seam, never the seam.

SSE framing, live

The framer (libs/http/sse/sse.odin) is a small incremental parser. It knows nothing about any provider — it only cuts a raw byte stream into completed data: payloads. The hard part is that TCP does not respect message boundaries: a chunk can end mid-line, split a \r\n, or split the leading BOM. Feed it below in whatever chunk sizes you like and watch the two buffers stitch events back together across the cuts.

The JS parser mirrors sse.odin exactly: a blank line dispatches only if a data: line was seen; event:/id: are parsed and dropped; multiple data: lines join with \n; a \r at a chunk tail sets last_was_cr so the next chunk's leading \n is swallowed as one CRLF.







  

    
Bounded, never asserting

    
1 MiB per line and per event. Overflow returns .Line_Too_Long/.Event_Too_Large, which the turn maps to .Response_Too_Large. Peer bytes degrade; they never crash the daemon — the decode boundary is error-return, not assertion.

  

  

    
Generic-looking, tuned to three

    
Dropping every field but data: is safe only because all three providers put the whole JSON object on one data: line. It reads generic; it is really a three-protocol framer.

  






Memory lifetime — the two arenas


This is the part worth getting exactly right, because every Stream_Event string is a borrow. A Turn owns two OS-backed virtual arenas and nothing else frees anything on this path — no decoder ever calls free. Three tiers of ownership, and one hard rule: scratch must never alias retained.




  

    
tier 1 · retained

    
turn lifetime

    
SSE buffers, every strings.cloned delta / signature / tool-arg byte, the event queue, the error prefix. Grows all turn; freed in one arena_destroy at cleanup.

  

  

    
tier 2 · scratch

    
one event

    
The parsed JSON tree for a single event. A arena_temp watermark is taken before decode and rewound after — pages are reused, never re-malloc'd. 8 MiB reserve so one event fits one block.

  

  

    
tier 3 · the borrow

    
until on_done

    
Emitted event strings point into retained. Valid only until the turn completes or cancels. The engine must clone anything it persists — the arena vanishes at on_done.

The alias ban is asserted right at the decode boundary — a clone that forgot to switch to the retained allocator would trip it before it could corrupt anything, because the next watermark rewind would free a string the decoder still holds.






And the whole thing is declared on one struct. Two arenas, an SSE parser, the decoder union, the event queue — the entire lifetime story of a turn is these fields.







  
Why events are queued, not fired inline

  
Curl calls the body sink from inside its own stack (in_libcurl). Firing a user callback there would re-enter curl illegally. So decode only appends to the queue; a zero-delay nbio.timeout_poly(0, …) drains it on a clean stack in turn_on_dispatch. The Completing state and the dispatching flag exist only to make cancellation safe while a borrowed event is on the user's stack. It is the most stateful piece on the path — and the one every reference harness solves by separating the pump from the pure decoder.

The Anthropic arm is the exemplar — a true event-typed protocol with an explicit block lifecycle and strict index ordering. The request side — where the rework lives


The three builders each walk request.messages once, forward-only, emitting literal JSON fragments (write_raw(",\"system\":")) with manual bookkeeping — message_count, block_count, hand-placed separators. The mapping logic (role-coalesce, tool reorder, empty-skip, thinking-replay gating) is duplicated three times.




  
The key observation. The request body is fully buffered into a strings.Builder before send. So forward-only writing buys no runtime benefit (unlike the response decoder, which genuinely streams) — it only inflates LOC and structurally blocks tail-caching. To mark "the last content block of the last message" with cache_control, you must know which block is last before you close it — which a forward-only writer cannot.






  

    approach:
    
    
  

  

    

  





The rework materializes a normalized block IR — []Message of []Block (text / thinking / redacted / tool_use / tool_result / image) — once from wire.Message, then hands it to a thin per-provider serializer. The shared pass (the LOC win) is the mapping; the per-provider part (relocated, not deleted) is the serializer, because the dialects genuinely differ. It lives in the scratch arena, bulk-freed by watermark rewind — no new arena type.




  

    
Random access unblocks the tail

    
blocks[last].cache_control = … — trivial once the IR exists. The whole reason for the rewrite.

  

  

    
One mapping, not three

    
Role-coalesce, tool reorder, empty-skip, replay gating collapse to a single pass feeding three small serializers.

  

  

    
Multimedia falls out free

    
An image/media Block arm is trivial once blocks are materialized — de-risks the planned multimedia work.

  




Don't oversell a 3→1 collapse. The mapping complexity relocates into the IR + serializer; it does not vanish. The honest win is: one shared builder + three small serializers, meaningfully fewer than 1,766 LOC, and every serializer gets random access.

Stable prefix — do first, ~3 lines

    
Switch system from a bare string to block-array form with one cache_control:{type:ephemeral}. Tools precede system in Anthropic's hierarchy, so one marker caches tools+system. No IR needed — ships before the rewrite.

  

  

    
Moving tail — the reason for the IR

    
Mark the last content block of the last message so growing history caches incrementally. Trivial once the IR exists (blocks[last].cache_control); ugly with a forward-only writer (a deferred-close hack).

  




Open gate: does the minimax compat endpoint accept cache_control blocks, or 400/ignore? Real api.anthropic.com is safe. Gate enablement on catalog cache pricing or an Anthropic allowlist; default off for compat. No auth edge cases — Anthropic is always Api_Key.

    •

Where we'd lead — or diverge

    
    
      
  • Ordered fallback lists per tier. None of the three has one — crush's tiers resolve to a single model, opencode/pi have no ladder. Our §4 "each tier is a fallback list" would put us ahead on resilience.
    •

  • Per-delta arg parse is optional. Only pi pays it, only for live-rendered args. Our defer-to-block-stop stance is the right default; revisit only if a client renders streaming tool input.

Push vs materialize — shaping the seam


fx surfaces one real fork the other harnesses also take a side on: how does a decoded part reach the engine? There are three shapes. fx pushes — the decoder calls a consumer function the instant it decodes. yuke materializes — the decoder produces a neutral Stream_Event value and a later tick delivers it. codex/opencode go one step further: a pure decoder plus an external pump. The call — and what the launch window is actually for

  
Keep the materialized Stream_Event seam. Callback-push is not a simplification for this codebase — it's a regression. Decode is pinned inside libcurl's non-reentrant write callback, and the queue-plus-tick is exactly the mechanism that lifts user code out of it. Every hand-rolled reference agrees: codex steps a decoder into an mpsc channel, opencode splits framing → protocol.step → executor, and even fx only pushes because its transport isn't a non-reentrant callback. The seam is a value for a reason.

  
The one worthwhile evolution is the pure decoder + pump (column 3): make each arm a pure (state, event) → [events] and move the Completing/dispatch handshake into one small explicit driver. Same wire behavior, a decoder that tests without any I/O, and the most-stateful-piece-on-the-path stops being threaded through Turn. But it's a refactor of a currently-correct, tested path — lower leverage than §1, and fully internal, so it's reversible after launch.

  
What the pre-release window is genuinely for is the wire surface, not this seam. The response seam and the request bodies are both internal / provider-facing — changeable any week. The decisions that are hard to make compatibly after 1.0 are the wire-protocol additions: §3's llm.complete method and §4's tier enum in src/wire. If those want to ship in 1.0, decide them now — spend the window there, and on §1's stable-prefix cache — not on reshaping a seam that already works.
