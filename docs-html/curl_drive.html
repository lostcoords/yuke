How the curl Drive works

Drive is the one adapter between libcurl’s socket-action API and core:nbio. Curl decides which sockets and timeout matter. Drive records those requests, translates them into nbio operations, and calls curl again only when something is ready. Client and connect-only Socket share this exact mechanism.

Two separate improvements

Why it is fast

The old driver called curl_multi_perform every 1–10 ms. Every response paid timer quantization even when its fd was already ready. The socket-action driver waits on the actual read/write fd or curl’s actual deadline. The local benchmark moved from about 44 requests/s to roughly 4,300 requests/s.

Why it is simpler now

The evented design necessarily has more concepts than periodic polling, but each fact now has one representation: one socket registry, one curl connect timeout, one explicit owner pointer, and one iterative pump. The simplification is fewer correlated states and fewer ways for them to disagree—not merely fewer source lines.

The mental model

Libcurl owns the HTTP/TLS state machine. nbio owns waiting. Drive owns only the translation between them. Owner-specific code deals with completion after curl returns.

owner ┌───────────────────────────────┐ │ Client │ │ many Transfer easy handles │ │ client_after_pump → On_Done │ └──────────────┬────────────────┘ │ explicit owner pointer │ ┌──────────────┐ ┌─────▼──────────────────────────┐ ┌──────────────────┐ │ core:nbio │ │ Drive │ │ libcurl multi │ │ │ │ watches[{fd,want,ops,owned}] │ │ │ │ poll Receive │◄────┤ timer_op ├────►│ HTTP / TLS state │ │ poll Send │ │ pumping / need_kick │ │ socket interest │ │ timeout │────►│ owner / after_pump │◄────┤ timer requests │ └──────────────┘ └─────▲──────────────────────────┘ └──────────────────┘ │ │ explicit owner pointer ┌──────────────┴────────────────┐ │ Socket │ │ one Connect_Only easy │ │ socket_after_pump → Connect │ └───────────────────────────────┘

Drive is still embedded because both owners expose its loop and multi internally, but correctness no longer depends on field offset zero. drive_init receives both owner and after_pump; the owner callback asserts that the pair matches.

One event cycle

Curl invokes its socket and timer callbacks while multi_socket_action is running. Those callbacks record desired state only. Once curl returns, Drive may dispatch completions and then reconcile nbio operations.

transfer_start / ready fd / curl timeout │ ▼ drive_kick or drive_pump │ ▼ ┌─ iterative pump loop ─────────────────────────────┐ │ in_libcurl = true │ │ multi_socket_action(fd, mask) │ │ ├─ drive_on_socket → record Watch.want │ │ ├─ drive_on_timer → record timer_ms │ │ └─ open/close socket callbacks update registry │ │ in_libcurl = false │ │ after_pump(owner) → drain Msg.Done │ │ │ │ need_kick? ─ yes ─► fd = SOCKET_TIMEOUT ──────────┤ │ │ continue immediately; no timer churn │ │ no │ │ ▼ │ │ drive_apply → arm/disarm nbio polls and timer │ └─────┬─────────────────────────────────────────────┘ │ ▼ event loop sleeps │ fd or timeout becomes ready └──────────────────────────► next pump

drive_apply is the commit-and-wait point

Curl's socket and timer callbacks only record desired state. This branch asks whether that state is final enough to install in nbio:

if !d.need_kick {
    drive_apply(d)
    return
}
need_kick == false

No more synchronous work was added. drive_apply commits the latest wishes by arming or disarming nbio polls and the timer, then the pump returns so the event loop can sleep.

need_kick == true

An On_Done callback started more work. The pump skips the intermediate nbio state and immediately calls curl again with SOCKET_TIMEOUT.

For example, curl may first request timer A, then a newly added transfer may replace it with timer B. Applying between those passes would arm A only to remove it immediately. The loop applies the final state once. Multiple starts in one pass collapse into one kick because the next socket action processes the whole multi handle; if that pass starts still more work, it sets need_kick again. The 10,000-immediate-failure regression exercises this iterative path without growing the stack.

One socket registry

A Watch now answers both questions: “what does curl want us to poll?” and “who closes this socket?” The fd is the identity; owned is the lifetime rule.

owned = true

drive_open_socket created it through nbio.create_socket. A curl Poll.Remove removes interest, not ownership: cached connections remain in the registry with no poll operations. The close callback or final destroy closes them synchronously.

owned = false

Curl exposed an fd we did not create, such as resolver work. Drive wraps and associates it with nbio. Association failure is returned to curl instead of being ignored. When curl removes interest, the registry entry can disappear; if curl later invokes its replacement close callback, that callback still closes the raw fd.

drive_close_socket uses net.close, not nbio.close. Libcurl’s callback replaces close(2), so the descriptor must be closed before the callback returns. Any armed poll is removed first.

Completion is a two-phase operation

client_after_pump first drains curl’s message queue into reusable scratch, then invokes application callbacks. Separating those phases keeps user code outside libcurl. The subtle part is that On_Done may start more transfers and grow the same scratch allocation.

curl message queue │ drain while in_libcurl ▼ completed = [A, B, C] count = 3 │ ├─ index 0: complete A → On_Done(A) │ └─ transfer_start(D, E) │ └─ reserve may move completed storage │ ├─ index 1: reload completed[1] from the current allocation │ B may already be canceled → skip unless Running │ └─ index 2: reload completed[2], complete C new curl work sets need_kick → iterative pump continues

The fixed count says which completions belong to this batch. Indexing reloads from the dynamic array after any reallocation. Checking Transfer.state handles another legal callback action: an earlier completion may cancel a later transfer before its queued message is dispatched.

Why Socket no longer has a second deadline

CURLOPT_CONNECTTIMEOUT covers name resolution and every protocol handshake until the remote connection is established—including TLS. Therefore deadline_op and CURLOPT_TIMEOUT duplicated the same bound. Keeping only the connect timeout also matters after success: a connect-only socket can legitimately live for hours, so it must not inherit a total-transfer deadline. The TLS-silent-peer regression still completes with Operation_Timedout.

Lifecycles and pinned addresses

Transfer Created ── transfer_start ──► Running ── curl done ──► Done │ │ └─ transfer_cancel ─► Canceled │ Done or Canceled ── start again ──┘ Socket Created or Closed ── socket_connect ──► Connecting │ ┌──────────┴──────────┐ ▼ ▼ Connected Failed │ │ └── socket_destroy ───┴──► Closed

Explicit owner pointers remove the offset-zero trick, but they do not remove address pinning. Curl stores ^Drive as callback data and nbio stores it in pending operations. A Client or Socket cannot move after initialization. Each running Transfer is also pinned because write/header callbacks retain ^Transfer.

in_libcurl

Guards regions that may call back or touch multi state: socket action, message drain, handle release, and cleanup. Starting, canceling, or destroying from a curl data callback is a programmer error.

pumping

Covers the entire iterative pump, including owner completion callbacks. On_Done is outside libcurl, so it may start another transfer; pumping converts that start into need_kick.

Walkthrough: one GET

  1. 1Start — validate the request, create/configure the easy handle, reserve live/completion storage, add the easy to the multi, mark Running, and kick Drive.
  2. 2Connect — curl resolves the host, asks the open callback for an nbio socket, begins a nonblocking connect, and requests send readiness plus a connect timeout.
  3. 3Wait — Drive applies nbio.poll(.Send) and the timer. The thread sleeps; there is no periodic curl tick.
  4. 4Write/read — readiness calls back into multi_socket_action. Curl advances TCP/TLS, writes the request, and changes interest to receive. Header/body callbacks borrow curl’s buffer for each call.
  5. 5Complete — curl queues Msg.Done. Client drains it after the socket action, reads status/error data, removes and cleans the easy, then calls On_Done.
  6. 6Idle or retry — if On_Done started work, continue the pump immediately. Otherwise reconcile to no armed operations. A cached owned connection may remain in the registry for reuse without costing an event-loop wakeup.
